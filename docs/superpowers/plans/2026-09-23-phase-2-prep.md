# Phase 2 Prep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the four items Phase 1's final review carried forward before any Phase 2 matchmaking/realtime code touches the affected files.

**Architecture:** Four independent, small changes: (1) extract one shared live-profile validity predicate used by both `live-profiles` and `discovery`, so the matchmaking pool (Plan A, next) has a third caller to reuse rather than a third hand-rolled copy; (2) move the API test suite from a single serialized Postgres instance to one schema per Vitest worker so the suite scales as Phase 2 adds tests; (3) make the mobile client react to a `401` by clearing the session, and add a real logout affordance; (4) add CI for both apps.

**Tech Stack:** TypeScript, Fastify, Drizzle ORM + `postgres-js`, Vitest, Expo Router, Zustand, Jest + `jest-expo`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-23-phase-2-matchmaking-design.md` §2 (prerequisite items), referencing the Phase 1 review carried forward in `docs/superpowers/plans/2026-09-21-project-roadmap.md` §8–9.

## Global Constraints

- `packageManager: pnpm@9.12.0` (root `package.json`) — use `pnpm --filter <pkg>` for per-app commands.
- Local Postgres/Redis come from `docker-compose.yml`: Postgres 16 on host port `15432` (user/pass/db all `pingo`), Redis 7 on `6379`.
- API env vars required at runtime/test time: `DATABASE_URL`, `REDIS_URL`, `JWT_ACCESS_SECRET`, `JWT_ACCESS_TTL` (see `apps/api/.env.example`).
- Backend tests run via `pnpm --filter @pingo/api test` (Vitest, `apps/api/vitest.config.ts` + `apps/api/vitest.setup.ts`); mobile tests via `pnpm --filter @pingo/mobile test` (Jest + `jest-expo`).
- Drizzle migrations live in `apps/api/drizzle/*.sql`, generated from `apps/api/src/infrastructure/postgres/schema.ts` via `pnpm --filter @pingo/api db:generate`, applied via `pnpm --filter @pingo/api db:migrate` (`apps/api/src/infrastructure/postgres/migrate.ts`).
- Existing test convention: every DB-backed test file calls `resetDatabase()` from `apps/api/test/testUtils.ts` in a `beforeEach`; do not bypass this convention.

## Review Focus

- A `401` on an **unauthenticated** request (e.g. login, register — called with `auth=false`) must never trigger a session clear; only a `401` on a request that actually carried a bearer token means the session is invalid.
- The home screen's new auth guard must not flash a redirect before `authStore` finishes hydrating from storage (mirror `index.tsx`'s `isHydrated` check) — otherwise every cold app start briefly bounces to `/login` before the stored token loads.
- `CREATE SCHEMA IF NOT EXISTS` for the per-worker test schema must be safe to run repeatedly and concurrently — Vitest's default `isolate: true` re-runs `setupFiles` per test file within a worker, so this runs many times per worker, not once.
- The shared live-profile predicate must not change existing behavior for `goLive`/`endLive`/discovery — the extraction is a refactor, not a behavior change, so all existing `live-profiles.test.ts` and `discovery.test.ts` assertions must keep passing unmodified.
- CI's Postgres service container needs a health check gate before migrations run against it, or the first CI run will flake on a race between container start and the app connecting.

```ts
// apps/api/src/modules/live-profiles/live-profiles.predicate.ts
import { and, eq, gt, type SQL } from 'drizzle-orm';
import { liveProfiles } from '../../infrastructure/postgres/schema.js';

export function isLiveProfileRowActive(
  profile: { status: string; expiresAt: Date },
  now: Date = new Date(),
): boolean {
  return profile.status === 'ACTIVE' && profile.expiresAt.getTime() > now.getTime();
}

export function liveProfileActiveCondition(now: Date = new Date()): SQL {
  return and(eq(liveProfiles.status, 'ACTIVE'), gt(liveProfiles.expiresAt, now))!;
}
```

- [ ] **Step 1: Write a test that proves two "workers" get isolated data**

This is an integration test that simulates what two Vitest workers do: open two `postgres-js` clients with different `PG_SCHEMA`-driven search paths against the same database and confirm a row inserted through one is invisible to the other.

```ts
// apps/api/test/schema-isolation.test.ts
import { describe, it, expect, afterAll } from 'vitest';
import postgres from 'postgres';
import { drizzle } from 'drizzle-orm/postgres-js';
import { migrate } from 'drizzle-orm/postgres-js/migrator';
import { users } from '../src/infrastructure/postgres/schema.js';
import { eq } from 'drizzle-orm';

async function clientForSchema(schemaName: string) {
  const client = postgres(process.env.DATABASE_URL!, {
    max: 1,
    connection: { search_path: schemaName },
  });
  await client.unsafe(`CREATE SCHEMA IF NOT EXISTS "${schemaName}"`);
  const db = drizzle(client);
  await migrate(db, { migrationsFolder: './drizzle', migrationsSchema: schemaName });
  return { client, db };
}

describe('per-schema test isolation', () => {
  const schemaA = 'test_isolation_a';
  const schemaB = 'test_isolation_b';
  let a: Awaited<ReturnType<typeof clientForSchema>>;
  let b: Awaited<ReturnType<typeof clientForSchema>>;

  afterAll(async () => {
    await a?.client.end();
    await b?.client.end();
  });

  it('does not see rows inserted into a different worker schema', async () => {
    a = await clientForSchema(schemaA);
    b = await clientForSchema(schemaB);

    await a.db.insert(users).values({ email: 'isolated@example.com', passwordHash: 'x' });

    const seenInA = await a.db.select().from(users).where(eq(users.email, 'isolated@example.com'));
    const seenInB = await b.db.select().from(users).where(eq(users.email, 'isolated@example.com'));

    expect(seenInA).toHaveLength(1);
    expect(seenInB).toHaveLength(0);
  });
});
```

```ts
import { useAuthStore } from '../auth/authStore.js';

const BASE_URL = process.env.EXPO_PUBLIC_API_URL ?? 'http://localhost:3000';

export class ApiError extends Error {
  constructor(public readonly status: number, public readonly code: string, message: string) {
    super(message);
    this.name = 'ApiError';
  }
}

async function request<T>(path: string, options: RequestInit = {}, auth = true): Promise<T> {
  const headers = new Headers(options.headers);
  if (options.body !== undefined) {
    headers.set('Content-Type', 'application/json');
  }

  if (auth) {
    const token = useAuthStore.getState().accessToken;
    if (token) {
      headers.set('Authorization', `Bearer ${token}`);
    }
  }

  const response = await fetch(`${BASE_URL}${path}`, { ...options, headers });
  const body = await response.json().catch(() => null);

  if (!response.ok) {
    if (auth && response.status === 401) {
      await useAuthStore.getState().logout();
    }
    throw new ApiError(response.status, body?.error?.code ?? 'UNKNOWN_ERROR', body?.error?.message ?? 'Request failed');
  }

  return body as T;
}

export const api = {
  get: <T>(path: string, auth = true) => request<T>(path, { method: 'GET' }, auth),
  post: <T>(path: string, payload?: unknown, auth = true) =>
    request<T>(path, { method: 'POST', body: payload ? JSON.stringify(payload) : undefined }, auth),
  del: <T>(path: string, auth = true) => request<T>(path, { method: 'DELETE' }, auth),
};
```

- None (CI workflow only; no application code).

- [ ] **Step 1: Write the workflow file**

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  api:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: pingo
          POSTGRES_PASSWORD: pingo
          POSTGRES_DB: pingo
        ports:
          - 15432:5432
        options: >-
          --health-cmd "pg_isready -U pingo"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    env:
      DATABASE_URL: postgres://pingo:pingo@localhost:15432/pingo
      REDIS_URL: redis://localhost:6379
      JWT_ACCESS_SECRET: ci-access-secret
      JWT_ACCESS_TTL: 15m
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9.12.0
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @pingo/api db:migrate
      - run: pnpm --filter @pingo/api typecheck
      - run: pnpm --filter @pingo/api test

  mobile:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9.12.0
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @pingo/mobile test
```

- [ ] **Step 2: Verify the workflow is syntactically valid YAML**

Run: `pnpm dlx yaml-lint .github/workflows/ci.yml 2>/dev/null || node -e "require('js-yaml').load(require('fs').readFileSync('.github/workflows/ci.yml','utf8'))"`
Expected: No error printed (if neither tool is available, a plain visual re-read against the block above is acceptable — this step exists to catch indentation mistakes, not to be a hard gate).

- [ ] **Step 3: Commit**

```bash
git add .github/workflows/ci.yml
git commit -m "ci: run api and mobile test suites on push and pull request"
```

- [ ] **Step 4: Push the branch and confirm the workflow runs**

Push this branch (or open a PR) and check the Actions tab: both the `api` and `mobile` jobs should appear and complete. This step has no local command — it's the first real-environment confirmation that the service containers, health checks, and migration step work together, which nothing in Steps 1-3 can verify locally.
